## 流程

新增房型正式儲存成功，先提供「建立此房型的房間／繼續新增房型」，不直接提供預約設定。前者清除使用者這段教學的舊暫停偏好，定位並展開傳入的確切 ID，手機回管理畫面；後者建立乾淨表單，保留已建立資料。

成功視窗本身只用暫時停罩旗標，不寫入永久暫停。主動稍後繼續才保存暫停，依帳號與店家隔離。

等待新 ID 時不回退第一筆房型；新目標、切店、離開或切換分頁使過期回呼失效。新 ID 消失時顯示狀態變更與重新確認／返回管理。資料到達同一個重建即分配穩定 Key，再定位原有房間操作區。

新增房間與快速建房沿用同一個 RoomManagementSection。快速建房開啟期間停罩，取消與零成功結果不呼叫成功通知；仍沿用既有數量、重複房號、批次結果與錯誤處理。串流先出現第一間房不會提前完成或導航。

成功事件後重新從伺服器讀取房間資格，確認目標房型底下有實際可用房間，沿用 enabled／永久狀態規則，不能只看上限或任意 rooms.length。沒有可用房間時提示處理現有房間，並提供手動重新確認。

確認房間後，使用 ShopPolicyService 的有效住宿條款判斷。缺條款則提供條款設定；已發布則提供預約設定。讀取失敗提供重試；點下一步再次讀取。條款導航檢查既有管理權限與方案；返回後再次判斷，未發布不往下。前往預約設定沿用同頁 callback／既有路由，保留開關 → 日期說明 → 手動儲存。

一般既有店家不因正常新增房間而強制重播開店教學；已具備房間的店家不因再新增房型重設全店準備狀態。

## 驗證

本次三個局部 Widget 案例通過：

1. 既有店家正常管理不觸發開店完成視窗。
2. 設定中心帶 guideStayOpening 補建房時保持房型分頁；明確前往預約時保留教學旗標，仍可返回補建房。
3. 390／1280 寬度下，連續建立兩個房型，表單乾淨、最新 ID 精確定位；串流晚到與目標消失不改選第一筆；舊暫停清除；新增與快速建房真實按鈕保留；單間表單取消回選擇；僅有數量上限、停用房間不完成；批次活動期間成功回呼不觸發檢查；結束後依條款判斷；讀取失敗重試；按下一步前條款狀態改變會重新判斷。

另只執行既有住宿測試中的兩個案例：`最小驗證：預約缺省、載入、有效狀態與舊店保留`、`住宿開放導引：真開關、日期說明與草稿保護`，通過。

測試透過注入的房型／房間串流、資格讀取及現有成功／批次活動 callback 模擬事件，未實際寫入任何正式資料。沒有把 callback 模擬當作真實快速建房批次寫入驗證。

未驗證：真實 Firestore 建房與批次部分失敗／重試、實際快速建房 Dialog／Bottom Sheet 的完整送出、真實條款發布後返回、真實瀏覽器及實體裝置觸控／鍵盤。

本次修改檔案執行格式與靜態檢查；設定中心另有其他任務新增區域的括號格式 info，未為此整理其內容。測試編譯一度被另一任務更新中的外觀相依檔阻擋，該相依後由原任務修正，本次未改動其外觀內容。
